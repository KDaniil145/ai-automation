# ParcelBot

Учебный React-интерфейс для классификации посылок и просмотра отправок по дате. Реализован по [критериям практики 8](https://github.com/ai-course-avito/ITMOv2/tree/main/practices/practice_08).

## Макет и библиотека компонентов

Для первоначального проектирования использован [исходный прототип ParcelBot в Figma Make](https://www.figma.com/make/7z26BI2zEUfAOxPbj4LIDR/ParcelBot-Parcel-Planning-Interface?t=v91Hh0vUxpOwoAKm-1). Его [сохранённый ZIP-экспорт](docs/design/ParcelBot%20Parcel%20Planning%20Interface.zip) содержит исходный React-проект с формой, списком, обеими темами и состояниями.

После доработок Codex итоговый визуальный макет автоматически собран из **реального текущего React-интерфейса**: Playwright снял экраны с моками API, затем скрипт собрал их в единую HTML-доску и экспортировал PNG. Дизайн по описанию не реконструировался, приложение ради съёмки не менялось.

- [Итоговая дизайн-доска PNG](docs/design/final/parcelbot-design-board.png) — 3520 × 9294 px, 1,87 MiB.
- [HTML-версия доски](docs/design/final/index.html) — статическая страница для просмотра; каждый кадр открывается отдельно. Для передачи сохраняйте всю папку final вместе с screens/.
- [Описание итогового макета и воспроизведение](docs/design/final/README.md).
- [Manifest с составом кадров и SHA-256](docs/design/final/capture-manifest.json).

Доска содержит **12 экранов**: форму и список в обеих темах, loading, success, empty, error и четыре мобильных кадра. Это актуальный статический экспорт финальной версии после работы Codex. HTML предназначен для просмотра макета; рабочее приложение запускается отдельно из frontend/. Исходный Figma Make и итоговая доска представляют два этапа проектирования.

Подтверждённые отличия от исходного прототипа:

| Исходный прототип | Итоговый интерфейс |
|---|---|
| Локальная классификация и хранение посылок | Расчёт/сохранение через WF1, чтение через WF2; localStorage только для темы и выбранной даты |
| Ручная кнопка «Показать отправки», сброс состояния вкладки | Автозагрузка при выборе даты; сохранение даты между вкладками и после перезагрузки |
| Общий счётчик вкладки и демо-надписи | Удалены; счётчик результатов выбранной даты сохранён |
| Нативные элементы управления | Mantine-компоненты с сохранением расположения, исходной палитры и обеих тем |
| Прежнее уведомление и неоднозначная заливка переключателей | Исправлены перенос уведомления и цвета on/off; добавлены реальные сетевые ошибки и повтор загрузки |

Новые снимки показывают эти изменения; исходный ZIP остаётся историческим прототипом.

Библиотека компонентов — **Mantine 8**: реальные `Button`, `TextInput`, `Switch`, `Notification`, `Paper`, `MantineProvider`. Поля и ошибки используют доступные связи label/input/description/error Mantine. Через `unstyled` и Styles API существующие CSS-токены Figma Make применены к готовым компонентам; поведение библиотеки сохранено. Tailwind из исходного проекта остаётся CSS-инструментом, требование компонентной библиотеки выполняет Mantine.

Единые цвета обеих тем заданы в `frontend/src/index.css`, типографика и шкала отступов — в теме Mantine в `frontend/src/App.tsx` и общих CSS-классах. Сохранены Manrope (с системным fallback), карточки, иконки, сетка и адаптивный список. После проверки прототипа удалены ручная кнопка загрузки, общий счётчик и демо-надписи; уведомление адаптировано к переносу текста. Текущие экраны: [скриншоты](docs/screenshots/), снятые браузерными тестами с моками API. ZIP сохраняет исторический макет; текущие скриншоты отражают согласованные изменения сценария.

Оба переключателя различают состояния цветом: включено — синяя дорожка и белый кружок справа, выключено — нейтральная серая дорожка и кружок слева. У переключателя темы справа соответствует тёмной теме, слева — светлой. Для приоритета используется `input:checked`: Mantine сохраняет атрибут `data-checked` и со значением `"false"`, поэтому проверка одного наличия атрибута давала неверную заливку. Оттенки выключенной дорожки — `#4b5563` в тёмной теме и `#9ca3af` в светлой. Скриншоты: [тёмная тема, приоритет выключен](docs/screenshots/toggle-dark-off.png), [светлая тема, приоритет выключен](docs/screenshots/toggle-light-off.png). Все четыре комбинации on/off перечислены в отчёте.

## Установка и запуск

Нужен Node.js 22.12+ (либо современная совместимая версия) и Corepack/pnpm. Повторный запуск проверен на Node.js 24.22.0 и pnpm 12.21.0.

```bash
cd frontend
corepack pnpm install --frozen-lockfile
cp .env.example .env.local
corepack pnpm dev
```

Открывайте **http://localhost:5173** из браузера Windows при запуске в WSL. Host Vite сохранён: `FIGMA_DEV_SERVER_HOST` либо `0.0.0.0`; dev-порт строго 5173. При занятом порте сервер завершится с ошибкой вместо перехода на другой Origin. `PORT` не переопределяет dev-порт. CORS для `http://localhost:5173` подтверждён владельцем проекта. `127.0.0.1`, HTTPS и другой порт — другие Origin.

В `.env.local`:

```dotenv
VITE_API_BASE_URL=https://n8n-itmo.cyrweb.ru/webhook
```

Это публичный базовый URL webhook, не URL редактора n8n и не секрет. После изменения перезапустите Vite; для production-сборки значение задаётся до сборки. Все `VITE_*` доступны браузеру: ключи и пароли туда не помещать. При отсутствии адреса показывается ошибка настройки, локального fallback-хранилища посылок нет.

```bash
corepack pnpm typecheck
corepack pnpm build
corepack pnpm preview --port 5173 --strictPort
```

Dev-сервер перед preview нужно остановить. Успешная сборка проверяет сборку, но не работу n8n и не бизнес-логику.

## Основной сценарий и API

Пользователь заполняет название, вес, дату и приоритет → при необходимости рассчитывает категорию → сохраняет посылку через WF1 → открывает «Отправки по дате» → видит сохранённую запись, полученную через WF2.

| Действие | Запрос относительно базового URL | Ответ |
|---|---|---|
| Расчёт WF1 | `POST /parcelbot-parcel`, `{ action: "calculate", weight, priority }` | 200, `{ category }` |
| Сохранение WF1 | `POST /parcelbot-parcel`, `{ action: "save", name, weight, priority, shippingDate }` | 201, `{ parcel }` |
| Список WF2 | `GET /parcelbot-parcels?date=YYYY-MM-DD` | 200, `{ parcels: [...] }` |

`parcel` содержит числовой `id`, `name`, числовой `weight`, boolean `priority`, `category`, `shippingDate`. Категории — `heavy`, `express`, `standard`. Вес > 10 даёт heavy при любом приоритете, иначе priority=true даёт express, false — standard. Клиент не вычисляет категорию, не генерирует ID и не сохраняет посылки локально. Контракт взят из обоих JSON в `workflows/`; работа GET, числовые ID и HTTP 200/201 дополнительно подтверждены владельцем проекта.

Вес должен быть конечным числом > 0, название после trim — 1–80 символов, дата — существующая календарная дата `YYYY-MM-DD`. Прошедшие даты API не запрещает. При ошибке валидации workflow возвращает HTTP 400 и `{ error: { code: "VALIDATION_ERROR", message } }`.

Список загружается автоматически при открытии вкладки и изменении корректной даты. Дата и тема сохраняются в localStorage; результаты — только в памяти, после перезагрузки читаются заново из WF2. При переключении вкладок дата и результаты сохраняются. Старые ответы не перезаписывают новую дату: используется AbortController и проверка номера запроса.

После сохранения список выбранной даты запрашивается заново, если она совпадает с датой посылки и список уже открывался. Старый GET инвалидируется до обновления. Сбой чтения не отменяет успешное сохранение. POST автоматически не повторяется: после потери ответа нужно проверить отправки перед повторной попыткой, поскольку серверная идемпотентность контрактом не предусмотрена.

Форма доступна с клавиатуры: Tab переключает элементы, Space меняет приоритет, Enter отправляет форму; есть видимый фокус, подписи полей и сообщения об ошибках. Пока выполняется запрос, поля и действия формы заблокированы; синхронный ref дополнительно защищает от двойного клика и повторной отправки Enter.

## Тесты

```bash
cd frontend
corepack pnpm test
corepack pnpm exec playwright install --with-deps chromium
corepack pnpm test:browser
```

Для Linux команда установки браузера с `--with-deps` может потребовать sudo. Если системные библиотеки не установлены, Chromium выдаёт, например, `libnspr4.so: cannot open shared object file`. Предпочтительно установить зависимости штатной командой выше. Для Ubuntu amd64 без sudo можно использовать независимый локальный кэш этого проекта:

```bash
# Из frontend/. Пакеты распаковываются, а не устанавливаются в систему.
mkdir -p .cache/browser-debs .cache/browser-libs
(cd .cache/browser-debs && apt download libnspr4 libnss3 libasound2t64)
for package in .cache/browser-debs/*.deb; do
  dpkg-deb --extract "$package" .cache/browser-libs
done
LD_LIBRARY_PATH="$PWD/.cache/browser-libs/usr/lib/x86_64-linux-gnu" corepack pnpm test:browser
```

Этот fallback применим к проверенной Ubuntu amd64; на другой ОС используйте системные зависимости Playwright. Кэш игнорируется Git, не зависит от других репозиториев и не нужен при наличии системных библиотек.

Vitest + React Testing Library + user-event проверяют видимое поведение, контракт HTTP, форму, компоненты, переключатели, темы, валидацию, loading/empty/success/error, повторные нажатия, смену даты с ответами в обратном порядке, сохранение даты и обновление списка после сохранения. Полный клиентский сценарий проверяет расчёт и сохранение через WF1, затем отображение **ответа WF2**, а не объекта из локального сохранения.

Playwright поднимает отдельный сервер на localhost:15173 с тестовым URL API, не затрагивая dev-сервер 5173. Он проверяет тот же путь клавиатурой в Chromium, фокус, перезагрузку, узкий экран, обе темы; создаёт скриншоты в `docs/screenshots/`. Для русских нативных полей даты заданы context `locale: "ru-RU"` и окружение запуска Chromium `LANGUAGE=ru_RU:ru`: на проверенной Ubuntu одного locale недостаточно. На пересозданных PNG поля даты показывают ДД.ММ.ГГГГ; значения API остаются `YYYY-MM-DD`. Диалогов в сценарии нет. `pnpm test:watch` запускает компонентные тесты в режиме наблюдения.

**Все автоматические тесты подменяют API.** В Vitest глобальный fetch заменён и неожиданное обращение отклоняется. В Playwright используется отдельный тестовый URL, ответы перехватываются, весь внешний трафик без мока блокируется. Тесты не создают записи в production n8n.

Полный запуск подтвердил **38/38 клиентских тестов и 3/3 браузерных теста**, TypeScript и production-сборку. После смены локали повторно прошли **3/3 браузерных теста**, TypeScript и проверка diff; Vitest и сборку на этом этапе не повторяли. Третий браузерный тест проверяет фактический цвет дорожек, белый цвет и положение кружков и подписи обоих переключателей в обеих темах. Скриншоты снимаются с отключёнными CSS-анимациями. На этой Ubuntu браузер использует локальные библиотеки из кэша ParcelBot, как описано выше.

[Отчёт проверки](docs/verification.md) содержит ограничения, проверку чувствительности тестов и полный перечень изменённых файлов. [Фактический вывод повторного запуска](docs/verification-output.txt) сохранён отдельно. Проверка чувствительности PASS → FAIL → PASS подтверждена [реальными журналами и manifest](docs/verification.md#проверка-чувствительности-тестов-реальные-доказательства), включая причину FAIL `Unable to find role="alert"` и совпадение контрольных сумм App.tsx и Git index.

## Ручная проверка production-интеграции

**Источник — ручные наблюдения пользователя через браузер**, сообщённые перед финальным ревью. Это отдельная проверка реального n8n, а не результат автоматических тестов:

- расчёт категорий `standard`, `express`, `heavy` работает;
- сохранение посылок через WF1 подтверждено; записи появились в n8n Data Table;
- подтверждены записи с **ID 3, 4 и 5**;
- WF2 отобразил сохранённые записи в React;
- после Ctrl + Shift + R данные сохранились и повторно загрузились;
- тёмная и светлая темы работают; включённые и выключенные состояния переключателей различаются цветом.

Агент не повторял production-запросы, не создавал и не удалял записи при подготовке отчёта. Точное время и версия браузера ручной проверки не предоставлены; автоматические скриншоты ниже не выдаются за свидетельство этой ручной проверки.
